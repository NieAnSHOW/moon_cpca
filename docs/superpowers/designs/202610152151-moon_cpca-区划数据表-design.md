## 1. 用户当前理解（认知校准结果）

来自 G1-Anchor 确认：本单元要的不是「把 CSV 复制进源码」，而是「一条**可复现、可机检、可追溯**的数据入库链路」。上游 cpca 把数据当包资源运行时读取（`cpca/resources/adcodes.csv`），MoonBit 侧零运行时依赖的要求决定了数据必须进编译期产物；但「直接抄进源码」会让 3511 行数据的同源性不可证。因此设计的核心问题是：**用什么产物形态 + 什么生成入口，使「入库数据 = 上游 CSV」成为一条可重跑命令的结论，而不是文档里的一句承诺**。

## 3. 关键约束（技术 / 成本 / 合规）

### 3.1 技术约束

1. **零运行时依赖**：产物与生成链路不得引入 `moonbitlang/core` 之外的运行时依赖（PRD FR-20 在引擎侧约束，本单元同理约束生成脚本不得成为构建必需）。
2. **编译期常量可行（已实测）**：3511 条记录的 Array 常量在本机 `moon test --target native` 编译并跑通（`probe/PROBE.md` §4 大数据表常量可行性段：`Total tests: 1, passed: 1, failed: 0`）。
3. **MoonBit 字符串形态**：`String` 的 `length()` 为 UTF-16 码元长度、`char_length()` 为字符长度，两者对非 BMP 字符差 1（`F:/Temp/posprobe/posprobe_test.mbt:2-3` 断言 char_length=10 / length=11）。数据表只存不改，故本约束只影响自校阶段的比对实现（比对必须用整串相等，不得逐码元）。
4. **平台目标**：本机 native 可用、wasm/js 不可用（PRD 9.2 风险表已登记 `[LOCAL_DEAD_LINK]`）。

### 3.2 平台接缝与本机目标分叉（PS1-PS3 / TB1-TB3）

**PS1 分叉能力登记**：

| 能力 | 分叉轴 | 接缝层位置 |
|------|--------|-----------|
| 数据表构建目标 | `moon build --target native`（本机可用）vs `--target wasm` / `--target js`（本机不可用） | `moon.mod` 的 `preferred_target = "native"` + CI 的 target 矩阵 |

**PS2 接缝收编**：目标分叉只出现在两处——`moon.mod` 的 `preferred_target` 声明与 CI 配置；数据产物本身的 `.mbt` 源码不含任何目标条件编译（已由 PRD FR-11「产物不含经纬度」同源纪律扩展到「产物不含平台分支」）。业务侧（引擎单元）面对统一的数据模块，零内联目标分支。

**PS3 一致性对照**：本工程为 greenfield（仓库仅有申报书 + 上游检出），无既有接缝模式可对照；`preferred_target = "native"` 的选择与引擎单元共用同一约定（兄弟 PRD 兼容性 NFR 同一口径），两单元的 target 声明必须一致，避免「数据表按 native 校验、引擎按 wasm 校验」的双口径。

**TB1-TB3 测试环境分支可测性**：数据产物层无平台分支（PS2 已清零），唯一分支是**构建目标选择**，而该分支由 moon 工具链处理而非被测代码——测试运行时不涉及目标分支解释。结论：`N/A — no platform branches in the data product; the only fork is the build target, owned by the toolchain, not by product code.`

### 3.3 渲染接缝（RS1-RS4）

`N/A — no shared UI files, no cross-engine render targets, no edge/bottom-docked elements.` 本单元交付的是数据源码与命令行工具，无界面产物。

### 3.4 成本约束

- 生成脚本用 Python（上游即 Python 生态，且本机已具备 3.12 + 上游可跑）；不引入额外语言运行时到构建链路。
- 3511 条常量编译耗时实测 < 0.4s（`probe/PROBE.md` §4 大数据表常量可行性段），无需为编译性能牺牲产物可读性。

### 3.5 合规约束

- 数据来源为公开行政区划信息（上游 MIT，本仓库 MIT），产物与 README 需注明出处与参考范围（PRD FR-08）。
- 无个人隐私数据，无跨边界数据流（PRD 10.7 已裁「无」）。

## 6. 设计决策追溯表

| 设计决策 | which/why 论证要点 | 回链 PRD 条目 | 代价（被弃项牺牲了什么） | 复开条件 |
|----------|--------------------|---------------|--------------------------|----------|
| **D-01 产物形态：单个 `Array[Record]` 编译期常量，`Record = { adcode, name, level }`** | 备选 A：拆成省/市/区三个扁平数组（检索快、体积略小）——否决：三个数组要靠索引隐式关联父子关系，重名区县的「多条并存」与「按行序回溯上游」都变得更难表达，且引擎侧要自行拼装；备选 B：嵌套结构 `省 → [市 → [区]]`——否决：上游数据本身是扁平 12 位 adcode，嵌套要额外推断父子，且直辖市「市辖区」这类特殊节点形态在嵌套里要特殊处理。单数组拿到的是：行序与上游逐行对应（FR-12）、重名多条并存天然成立（FR-10）、引擎侧可按需自建索引 | FR-01、FR-02、FR-10、FR-12 | 放弃了三数组的检索速度与嵌套的可读性；引擎侧需自行建索引（其代价由引擎单元承担） | 引擎单元实测表明单数组建索引后单条提取 > 5 ms（PRD 引擎 NFR 性能行） |
| **D-02 `level` 在入库时派生并随记录存储，而非引擎侧现算** | 备选：引擎侧每次按 adcode suffix 现算——否决：自校（FR-05）需要统计三档计数，若 level 不入库，自校逻辑与引擎逻辑各写一份 suffix 规则，双口径漂移风险。入库时派生 + 自校同源，一处规则两处消费 | FR-01、FR-05 | 每条记录多存一个枚举字段（体积/可读性代价） | 上游改变 adcode 编码规则导致 suffix 派生失效（PRD 10.5 已登记该假设） |
| **D-03 生成入口为仓库内 Python 脚本（`tools/gen_adcodes.py`），输入上游 CSV，输出 `.mbt`** | 备选 A：MoonBit 侧脚本生成——否决：MoonBit 侧读 CSV 需文件 IO 能力，且本机 native 之外的运行通道不可用，等于把数据链路绑死在单一目标；备选 B：直接把 CSV 提交进仓库让用户在构建期读取——否决：违背零运行时依赖。Python 是与上游同生态的最低摩擦选择，且生成逻辑可与上游 oracle 复用同一进程 | FR-04、US-01 | 数据链路的「权威生成器」依赖 Python 环境（贡献者需装 Python）；换来了可复现 + 可自校 | MoonBit 生态出现稳定的文件 IO + CSV 解析组合且本机 wasm/js 通道恢复 |
| **D-04 产物行序 = 上游 CSV 行序，不做排序** | 备选：按 adcode 排序输出以获得稳定 diff——否决：排序让「产物第 N 条 = 上游第 N 行」的回溯关系断裂（FR-12），且上游数据本身有序（首批记录即 `500233000000,忠县`）。上游行序变化时 diff 非空的代价，由 CI 的 golden 一致性门禁显式暴露（这恰是想要的行为：数据变了就要人看一眼） | FR-12、G-01 | 上游若重排数据行，diff 会非空并要求人工确认（放弃「永远自动 diff = 0」） | 上游出现无预警的行序重排且频繁到需要免疫 |
| **D-05 自校作为生成命令的内置步骤（非独立脚本），失败即非零退出** | 备选：自校作为独立校验命令、生成命令只负责产出——否决：分开意味着「生成了但没自校」是可达状态，维护者容易跳过。内置使「导出成功」蕴含「自校通过」 | FR-05、FR-06、FR-09、NFR 失败可诊断性 | 生成命令职责变重（产出 + 校验一体），单独重跑校验需加 flag | 自校耗时增长到影响生成命令可用性（当前 3511 条为毫秒级） |
| **D-06 来源标识写入产物文件头注释（而非只写 README）** | 备选：只写 README——否决：README 与产物可脱耦分发（发布到 mooncakes 的包里使用者读不到本仓库 README 的上下文），产物头注释随包走 | FR-07、US-04 | 产物文件头部多几行注释（体积/纯净度代价） | MoonBit 包元数据（moon.mod 的 description/keywords）被证明足以承载来源标识 |

## 7. 降级路径 + 数据流方向

**FE1 降级路径**：本单元无主/降级路径之分——生成命令要么成功产出（含自校通过），要么非零退出并给出诊断。唯一近似「降级」的形态是**自校失败时的处置**：不是降级为「产出未校验数据」，而是显式失败（PRD FR-05 验收 ②：篡改数据 → 非零退出）。理由：数据层的静默降级会直接把错误数据送进引擎，而引擎的 golden 比对只会报告「行为不符」无法归因到数据——降级反而放大诊断成本。判定：`无降级路径；自校失败 = 显式失败，非降级`。

**FE3 外部依赖前置条件**：主路径硬依赖 = 上游 CSV 文件存在于本地检出。缺失时的可观察行为已由 PRD FR-09 定义（文件缺失/空/列名不符三类 → 非零退出 + 指明文件名/列名）。上游仓库随本仓库 vendored（`chinese_province_city_area_mapper/`），不是网络依赖。

**DF3 数据流方向**：`N/A — no sensitive data flow.`（PRD 10.7 已裁「无」；产物为本地源码文件，生成不发起网络请求。）
