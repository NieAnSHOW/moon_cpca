## 一、问题陈述

> 本单元解决的问题：一份**可复现、可核对、可随数据版本更新**的中文行政区划数据表，是 moon_cpca 库的地基。上游 cpca 把数据藏在 Python 包资源里（`cpca/resources/adcodes.csv`，运行时经 `resource_stream` 读取），MoonBit 侧若照搬「运行时读文件」，就会违背申报书「库本身零第三方运行时依赖」的承诺；若直接手抄进源码，F1-1 行数的数据无人能核对「入库的就是源数据」。
>
> 目前的做法（截至本 PRD）是「上游 CSV 直接进 MoonBit 源码」这条无法验证的路径：数据一旦与上游产生偏差（漏行、错列、adcode 截断口径不一致），MoonBit 版与 Python 版的解析结果就会在边界用例上分叉，而这种分叉在移植完成前无任何手段可发现。

**量化事实（唯一事实表 F1，正文只引用编号）**：

| 编号 | 断言 | 可机检域定义 | 命令 | 结果 |
|------|------|-----------|------|------|
| F1-1 | 上游区划数据共 3511 条记录 | `chinese_province_city_area_mapper/cpca/resources/adcodes.csv` 的全部数据行（不含表头） | `python -c "import csv;print(len(list(csv.DictReader(open('chinese_province_city_area_mapper/cpca/resources/adcodes.csv',encoding='utf8')))))"` | 3511 |
| F1-2 | 记录按 adcode 前缀分级为 34 省级 / 344 市级 / 3133 区县级 | 同一 CSV 全表，按 adcode 前 6 位uffix（0000=省、00=市、其余=区县）分档计数 | `python -c "import csv,collections;r=list(csv.DictReader(open('chinese_province_city_area_mapper/cpca/resources/adcodes.csv',encoding='utf8')));[print(k,v) for k,v in collections.Counter('P' if x['adcode'][:6].endswith('0000') else 'C' if x['adcode'][:6].endswith('00') else 'A' for x in r).items()]"` | P=34, C=344, A=3133 |
| F1-3 | 名称唯一数 3182、重名名称 31 个 | 同一 CSV 的 `name` 列 | `python -c "import csv,collections;n=collections.Counter(x['name'] for x in csv.DictReader(open('chinese_province_city_area_mapper/cpca/resources/adcodes.csv',encoding='utf8')));print('unique',len(n),'dup',sum(1 for v in n.values() if v>1))"` | unique 3182, dup 31 |
| F1-4 | 上游 Python 实现共 426 行（含 `__init__.py` 248、`matcher.py` 97、`structures.py` 60、`exceptions.py` 21） | 四个 `.py` 源文件行数合计 | `wc -l chinese_province_city_area_mapper/cpca/*.py` | 426 |

**现状表述**：做中文地址归一的开发者（订单分析、日志地理归因、表单联动）拿不到一个「数据与上游同源、且同源性可机检」的 MoonBit 区划表。Python 用户有 cpca（CSV 随包发布），MoonBit 生态空白（申报书已查重）。若不做本单元，`moon_cpca` 的匹配引擎（兄弟单元）将在「数据可信度不可证」的地基上建造，解析结果的任何偏差都无法归因到数据层还是算法层。

## 二、目标

| 目标编号 | 目标描述 | 衡量指标 | 目标值 | 当前值 | 衡量时间 |
|----------|----------|----------|--------|--------|----------|
| G-01 | 区划数据从上游 CSV 到 MoonBit 源码的转换由仓库内可重跑脚本完成，任何人无需手工介入即可复现同一份数据表 | 从干净检出（clean checkout）跑一次生成命令后，`.mbt` 数据文件与仓库内提交版本的逐字节差异 | 0 字节 | 当前无生成脚本（差异不可测） | 数据表单元交付时 |

| G-03 | 数据的等级结构与重名情况在入库时被自校，防止等级判定口径（adcode 后缀规则）在转换中被写错 | 生成产物内含的等级/重名统计与对上游 CSV 直接统计的结果一致数 | 四级分档计数（省/市/区县/总行数）与 F1-2、F1-1 逐项一致；重名名称数与 F1-3 一致 | 当前无自校 | 数据表单元交付时 |
| G-04 | 数据版本与来源在产物与文档中可追溯，使用者可判断「这份表对应上游哪一版」 | 产物中记录的来源标识（上游文件路径 + 记录数 + 上游内容指纹/提交标识，输入决定、可复现）可在产物内定位 | 1 处来源标识，含上游文件名与记录数 | 当前无 | 数据表单元交付时 |

## 三、非目标

| 非目标 | 排除原因 |
|--------|----------|
| 区划数据的语义加工（简称归一、别名表、停用词表） | 属匹配引擎单元（兄弟 PRD）的输入契约，不在本单元；本单元只交付「与上游同源的原始数据」 |
| 街道/门牌号级数据 | 申报书明确不做（无权威数据源、误差不可控），上游 cpca 亦不做 |
| 经纬度与逆地理编码数据 | 属 geocoding 语义域，申报书明确不做；上游 CSV 虽含 longitude/latitude 列，本库不消费 |
| 区划数据在线更新服务 | 申报书明确不做（数据随包版本化发布即可满足）；本单元只交付静态生成链路 |
| MoonBit 侧的匹配算法与 extract API | 属兄弟 PRD「提取引擎」单元，本单元以数据文件为交付边界 |

## 四、用户故事

```
用户角色：库维护者（数据更新者）、库消费者（MoonBit 使用者）、移植验收者
```

### US-01【P0】库维护者复现数据表

作为库维护者，我想要在干净检出上跑一条命令就重新生成区划数据表，以便上游区划年度更新时无需手工改 F1-1 行数的源码、也不会因手工抄写出错。

验收标准：
1. 干净检出状态下执行数据生成命令，命令退出码为 0，并在约定位置产出 `.mbt` 数据文件（Yes/No）。
2. 产出文件与仓库内已提交版本逐字节一致（diff 为空，Yes/No）。
3. 生成过程不依赖 network（不发起任何外部请求，Yes/No）。

### US-02【P0】验收者核对入库数据与上游一致

作为移植验收者，我想要机检「入库数据 = 上游 CSV」，以便在算法行为分叉时能先排除数据层原因。

验收标准：
1. 机检报告入库记录数与 F1-1 一致（Yes/No）。
2. 逐条比对 adcode 与 name 与上游 CSV 对应行，不一致数 = 0（Yes/No）。
3. 比对命令本身可重跑，且输出不一致条目明细（而非仅布尔结论，Yes/No）。

### US-03【P1】维护者判断数据表等级自校是否通过

作为库维护者，我想要生成时自动校验等级结构与重名统计，以便上游调整 adcode 后缀规则或出现意外重名时立刻发现。

验收标准：
1. 生成命令输出省/市/区县三档计数与总行数，且与对上游 CSV 直接统计的 F1-1/F1-2 一致（Yes/No）。
2. 生成命令输出重名名称数，且与 F1-3 一致（Yes/No）。
3. 统计口径与上游 CSV 的统计口径在产物中写明（adcode 前 6 位后缀规则），可人工核对（Yes/No）。

### US-04【P1】使用者追溯数据表版本来源

作为库使用者，我想要从产物或文档看出这份区划表来自上游哪个文件、哪一版，以便评估数据时效。

验收标准：
1. 产物内含来源标识，至少含上游文件名与记录数（Yes/No）。
2. README 注明数据来源（上游项目名 + 文件路径 + 许可证 MIT）与数据版本说明（Yes/No）。

## 五、需求详细说明

### 5.1 功能需求（FR）

| 需求ID | 需求描述 | 所属用户故事 | 优先级 | 验收标准 |
|--------|----------|--------------|--------|----------|
| FR-01 | 产物是一份 MoonBit 源码文件，内含与 F1-1 同条数的行政区划记录结构化编译期常量（每条含 adcode 与 name），可被 MoonBit 编译器直接消费 | US-01 | P0 | ① 文件可被 `moon build --target native` 编译通过；② `inspect(记录数组长度)` 与 F1-1 一致；③ 数组内每条记录含 adcode 与 name 两个字段 |
| FR-02 | 记录的字段口径与上游 CSV 逐列一致：adcode 取上游 12 位原值，name 取上游原值（不做大小写/空白/全半角加工） | US-02 | P0 | 机逐条比对：adcode/name 字段与 CSV 对应行相等，不一致数 = 0 |
| FR-03 | 产物内 adcode 与 name 的表示形态满足：adcode 为 12 位定长字符串原样保存，name 为 Unicode 字符串原样保存（含 15 字上限的最长名） | US-02 | P0 | ① 任意抽样记录的 adcode 长度 = 12；② 机检出最长 name 长度 = 15（`python -c "import csv;print(max(len(x['name']) for x in csv.DictReader(open('chinese_province_city_area_mapper/cpca/resources/adcodes.csv',encoding='utf8'))))"` → 15）；③ 超长名记录在产物中完整可读 |
| FR-04 | 仓库内存在单一权威数据生成入口（脚本），输入为上游 CSV，输出为 MoonBit 数据文件；入口的唯一性可识别（README 或 Makefile 指明） | US-01 | P0 | ① 从仓库根可用一条固定命令触发生成；② 生成产物位置固定；③ 入口命令在 README 有记载 |
| FR-05 | 生成过程对等级结构做自校：按 adcode 前 6 位 suffix 规则（0000=省、00=市、其余=区县）统计三档计数与总行数，与上游 CSV 统计不一致时生成失败（非零退出） | US-03 | P1 | ① 正常数据下退出码 = 0 且输出分档计数与 F1-2 一致、总行数与 F1-1 一致；② 构造篡改数据（改一条 adcode 后缀）→ 退出码非 0 且输出不一致项 |
| FR-06 | 生成过程对重名情况做统计并写入产物/报告，重名名称数与上游 CSV 统计一致 | US-03 | P1 | 重名名称数 = 31（F1-3）；报告可重跑复现同一数值 |
| FR-07 | 产物内含来源标识，且标识由输入决定（上游文件名 + 记录数 + 上游 CSV 内容 hash/提交标识），可复现（禁墙钟时间戳，否则重生成 diff 永不为 0） | US-04 | P1 | ① 产物中可定位单一来源标识注释行；② 标识含上游文件名与 F1-1 记录数；③ 重生成后 diff = 0 字节（G-01 验收）；④ 标识中不含墙钟时间戳 |
| FR-08 | README 记载数据来源与许可证归属（上游 cpca / MIT / 参考范围），与仓库根 LICENSE（MIT）一致 | US-04 | P1 | ① README 含上游项目链接与 MIT 说明；② 仓库根存在 LICENSE 且为 MIT |
| FR-09 | 数据生成入口对「上游 CSV 缺失/为空/列名不符」三类输入异常有可观察的失败行为（非静默产出空表） | US-01 | P1 | ① CSV 缺失 → 退出码非 0 且错误信息指明缺失文件；② CSV 只有表头无数据行 → 退出码非 0；③ 缺 adcode 或 name 列 → 退出码非 0 且指明列名 |
| FR-10 | 重名区县在产物中保持「多条记录并存」形态（同名不合并、不去重），供兄弟单元做上级市消歧 | US-02 | P0 | ① 机检重名名称（如朝阳区）对应记录数 ≥ 2；② 各记录 adcode 不同且全部在产物中 |
| FR-11 | 上游 CSV 的 longitude/latitude 列不被消费（产物中不出现经纬度字段） | US-02 | P1 | 机检产物中不含 longitude/latitude 标识（grep 命中数 = 0） |
| FR-12 | 产物中数据的排列顺序与上游 CSV 行序一致（便于按行号回溯上游） | US-02 | P2 | 逐行比对：产物第 N 条 = CSV 第 N 行（首条为 `500233000000,忠县`，末条可重跑取） |

> **同对象多 FR 交互矩阵**：本单元触及对象 = 「产物记录集」「生成入口」「来源标识」。
> - 对象「产物记录集」× FR-02 × FR-10 × FR-12：正常情况下记录集同时满足「字段与上游一致」「重名多条并存」「顺序与上游一致」三条；若上游数据更新导致记录数变化，三条同时以新数值为准（不出现「FR-02 用新数、FR-12 用旧数」的双口径），验收时以同一次生成产物为唯一对象。
> - 对象「生成入口」× FR-04 × FR-09：正常输入归 FR-04（产出固定位置文件）；输入异常时归 FR-09（非零退出），FR-04 的「产出文件」承诺在异常态下不适用（异常态产物文件不存在或不被更新）。
> - 无其他同一对象被 ≥2 条 FR 触及的情形。

### 10.6 PRD 拆分声明

**为什么拆**：moon_cpca 需求覆盖「数据表」与「匹配引擎」两个可独立交付、独立测试的子系统（触发条件 1：≥2 个可独立交付子系统；触发条件 4：整体超出单个 AI 上下文窗口可完成范围，上游实现 426 行（F1-4）+ F1-1 条数据 + MoonBit 引擎 + golden 测试一次性写成必然中途崩溃）。按独立可展示交付物纵切为两份，禁止按实施时序阶段横切。

| 归属 | 覆盖单元 | 共享接口/边界（与兄弟 PRD 对齐） | spec 承接 |
|------|----------|----------------------------------|-----------|
| 本 PRD 为拆分之一（共 2 份） | 区划数据表单元：上游 CSV → 可复现生成的 MoonBit 编译期数据产物 + 自校 + 来源标识 | ① 产物记录字段（adcode/name/level）与排列顺序是兄弟单元「提取引擎」的输入契约；② 兄弟单元不得自带第二份数据源，只消费本单元产物；③ 兄弟单元所需的重名多记录并存形态由本单元 FR-10 保证 | 单个 spec：`[time]-moon_cpca-区划数据表-spec.md` |
| 兄弟 PRD | 提取引擎单元：extract API + 匹配语义 + golden 对照测试 + README/CI/publish | 同上（镜像登记） | 单个 spec：`[time]-moon_cpca-提取引擎-spec.md` |

**单单元验收可达性验证结论**：
- 本 PRD（数据表单元）：**可达**。只完成本单元（兄弟单元未交付）时，G-01..G-04 与 FR-01..FR-12 均可独立观察——数据表可编译、可 diff、可机检比对、可复现异常输入，不依赖任何兄弟单元功能。
- 兄弟 PRD（提取引擎单元）：**可达**。其验收所需的数据输入由本单元产物以静态数据文件形式提供，不要求本单元的生成脚本已交付（引擎侧锁定数据文件的消费契约即可）。

### 10.7 敏感数据流声明

**无**。本单元处理公开行政区划数据（adcode/name），不含可定位到个人或隐私的数据，不产生任何跨边界数据流：产物为本地源码文件，生成过程不发起网络请求（US-01 验收标准 3 以「不发起任何外部请求」为 Yes/No 判据）。
