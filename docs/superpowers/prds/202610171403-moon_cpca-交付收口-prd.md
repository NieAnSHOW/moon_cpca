## 三、非目标

| 非目标 | 排除原因 |
|--------|----------|
| 算法行为变更（匹配顺序、消歧、addr 截断等语义调整） | 本单元只收口交付面；行为基准已由 32 条 golden 与差分 harness 锁定，改行为会使既有对齐失效 |
| 多地址长文本 API（`transform_text_with_addrs`） | 申报书只列单条 `extract`；该能力另立未来 PRD，本单元只保证差异声明可见，不静默删除已声明范围 |
| 街道/门牌号级解析、经纬度/逆地理编码、区划数据在线更新服务 | 申报书明确不做，且无权威数据源与在线服务边界 |
| 发布包内容瘦身（排除 docs/tools/testdata/probe/申报书） | 属发布策略取舍，需先确认 mooncakes 对包内容与体积的约束；本单元只记录为开放问题，不改变包内容 |
| 超出已列对齐缺口的 P2 quirk 回归（单字键 `县`/`芒`、候选数大于 2 的同名区等） | 与上游同源同行为，差分 harness 已覆盖；本单元只补申报书验收直接依赖的上游用例输入 |
| 原样运行上游 Python 测试套件 | 上游 `test_cpca.py` 依赖缺失的 `mock` 模块无法收集；本单元以「输入 + 上游期望值」逐条对齐，不把运行上游套件作为交付条件 |
| 重构引擎内部结构或替换匹配数据结构 | 与本单元目标无关，且会引入未受 golden 保护的行为风险 |

## 四、用户故事

```
用户角色：库维护者、发布者、MoonBit 消费方、移植验收者、文档读者
```

### US-01【P0】维护者在全新 clone 上复现数据与 golden

作为库维护者，我想要在全新 clone 上运行一个权威再生入口，以便不依赖本机残留文件即可确认交付物可复现、可更新。

验收标准：
1. 全新 clone 后执行 `python tools/regen.py`，退出码为 0；`git diff --exit-code` 退出 0；提交态 `data/adcodes.mbt` 经 `python tools/check_artifact.py --records --fields --levels --order --dup` 退出 0（Yes/No）。
2. 全新 clone 后按 README 安装 oracle 依赖，`python -c "import pandas, ahocorasick"` 退出 0；执行 `python tools/regen.py` 与 `python tools/check_golden.py`，两者退出码均为 0，`cases=N` 中 N 等于 `wc -l testdata/golden.jsonl`；`git diff --exit-code` 退出 0 且 `git status --short` 为空（Yes/No）。
3. 缺失类失败路径：故意移走 vendored CSV 后运行 `python tools/regen.py`，命令退出非 0，stderr 指出缺失文件的仓库相对路径，且不写出半成品产物（Yes/No）。
4. 网络隔离路径：`python tools/regen.py --no-network-check` 在禁止网络的审计下退出 0，报告中的网络事件计数为 0（Yes/No）。
5. 全新 clone 上 `moon fmt --check` 退出 0；权威再生入口完成后再次检查仍退出 0（Yes/No）。

### US-02【P0】发布者把 v0.1.0 发布到 mooncakes

作为发布者，我想要清单身份与仓库引用在发布前一次通过校验，并完成 0.1.0 首发，以便消费者能从注册表获取该版本。

验收标准：
1. `moon publish --dry-run` 输出含 `Server status: 202 Accepted` 与 `Dry run completed successfully`，且无 manifest 字段 warning/error；退出码 255 本身不判失败（Yes/No）。
2. 真实发布返回 `Server status: 200 OK`，且 `moon view vicoproplus/moon_cpca --versions` 的输出包含 `0.1.0`（Yes/No）。
3. 凭证缺失类失败路径：未登录时发布退出非 0，错误信息含鉴权状态，且注册表不产生新版本（Yes/No）。
4. 权限拒绝类失败路径：服务端返回 403 时，错误信息含模块名与权限语义，本次发布尝试次数不超过 1，不进入自动重试循环（Yes/No）。
5. 版本冲突类失败路径：重复发布 0.1.0 时服务端返回冲突语义，错误信息含版本号，已存在版本内容不被覆盖（Yes/No）。
6. 仓库发布状态：`git rev-list --count origin/main..main` = 0，`git tag -l v0.1.0` 非空，tag 指向的提交与 `origin/main` HEAD 一致且该提交的 CI 运行成功（Yes/No）。

### US-03【P0】消费方在 native 与 wasm-gc 上安装并使用

作为 MoonBit 消费方，我想要从 mooncakes 安装 `vicoproplus/moon_cpca@0.1.0` 并在 native 与 wasm-gc 目标上编译通过，以便在真实项目中调用 `extract`。

验收标准：
1. 全新消费方模块执行 `moon add vicoproplus/moon_cpca@0.1.0`，退出码为 0，依赖出现在清单中（Yes/No）。
2. 消费方 `moon build --target native` 退出 0；调用 `extract("徐汇区虹漕路461号58号楼5楼", pos_sensitive=true)` 得到省=上海市、市=市辖区、区=徐汇区、adcode=310104（Yes/No）。
3. 消费方 `moon build --target wasm-gc` 退出 0；CI 运行记录中出现 wasm-gc 测试二进制的用例计数（执行成功）。该证据缺失时发布保持阻断，不登记为 unresolved（Yes/No）。
4. 目标不可用类失败路径：wasm-gc 的 loader/runner 缺失时，错误信息指出目标名与实际缺失的运行器，发布保持阻断直至补齐并重跑；js 的 runner 缺失时状态记录为「unresolved + 具名原因」（Yes/No）。
5. js 目标在兼容性矩阵中的状态非空，且只能是「green（有运行记录）」或「unresolved（具名原因）」（Yes/No）。

### US-04【P0】验收者按上游用例逐条核对行为

作为移植验收者，我想要上游 `test_transform` 与 `test_umap` 的每条输入都能在 MoonBit 用例集中找到对应条目与逐字段期望，以便把「与 Python 用例集交叉对照」从子集声明变成可逐条判定的结论。

验收标准：
1. 11 条单条提取输入在覆盖映射表中逐条登记；其中 10 条字符串输入对省/市/区/addr/adcode 与三项 pos 逐字段比对，整型 `32323` 单独标记为类型层 N/A 并写明 `extract` 只接受字符串（Yes/No）。
2. 「天津市」补齐省/市/区/addr/adcode 与三项 pos 的断言；「淮安市市辖区」补齐 addr 断言（Yes/No）。
3. 两条 umap 输入均有用例：第一条 + umap 得 110105；第二条 + umap 且已有上级时仍得 220104（Yes/No）。
4. `pos_sensitive=false` 与不传该参数时三个 pos 均为 -1；README 的「与上游差异」段落声明上游此时不输出 pos 列（Yes/No）。
5. 差异定位路径：任一条目字段不一致时，报告文件含输入、期望、实际、首个不一致字段四项，且四项均可检索（Yes/No）。

### US-05【P1】文档读者按 README 安装、运行示例并取失败报告

作为文档读者，我想要 README 的安装、快速开始、兼容性、数据更新与上游差异五段可直接照做，且仓库内 example 能真的跑出注释所示输出，以便判断这个包是否适合我的项目。

验收标准：
1. README 五段标题均可检索，安装命令可在全新消费方直接复制执行（Yes/No）。
2. 仓库内 example 包在 native 目标运行退出 0，stdout 与 README 快速开始代码块的注释值逐行一致（Yes/No）。
3. README 的失败诊断命令仅捕获 stderr（`2>`），构造一条不一致后报告文件存在且四项均可检索；无失败时命令退出 0 且报告文件为空（Yes/No）。
4. 兼容性矩阵逐目标列出 native / wasm-gc / js 的状态，无空白行（Yes/No）。
5. `CHANGELOG.md` 的 0.1.0 段与兼容性矩阵、数据 sha256 声明一致（Yes/No）。

### 10.6 PRD 拆分声明

**单份 PRD，无需拆分。**

理由：本单元的全部 FR 服务于同一个发布门——「v0.1.0 可发布且可验收」。按实现时间阶段拆成多份 PRD 会产生依赖死锁：发布（FR-05～FR-07）依赖干净 clone 的复现链路（FR-01～FR-04）先落地；CI 门禁（FR-08～FR-10）依赖快照入库与格式收敛；文档与示例（FR-15～FR-18）依赖最终模块名与真实包行为。拆开后任一子 PRD 都无法独立验收，只能互相等待。实现阶段会在计划中拆成小任务（快照入库、清单改名、CI 扩展、用例补齐、示例与文档），但不拆本 PRD。

| 归属 | 覆盖单元 | 共享接口/边界（与兄弟 PRD 对齐） | spec 承接 |
|------|----------|----------------------------------|-----------|
| 单份 PRD，无需拆分 | 本 PRD 全部 FR-01～FR-20 | 模块名 `vicoproplus/moon_cpca`；包路径 `vicoproplus/moon_cpca/data` 与 `vicoproplus/moon_cpca/engine`；golden 上游版本锚 `0.5.5`；`extract(text, pos_sensitive, umap)` 公开面不变；`tools/regen.py` 为唯一权威再生入口，裸 `gen_adcodes.py` / `gen_golden.py` 为下层入口；旧数据 PRD/spec 中「裸生成器输出逐字节一致」的发布产物契约由本 PRD 取代，不再作为发布验收口径 | 单个 spec |
